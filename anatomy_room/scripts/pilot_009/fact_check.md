# pilot_009：事実確認リスト（結局、今回のPHP騒動は何だったの？）

調査日：2026-10-26（同日、冒頭の問いを追加した v2 に合わせて行番号を更新）。確認方法の定義は `docs/FACT_CHECK_POLICY.md`、調査環境の制約は `docs/RESEARCH_ENVIRONMENT.md`。

**この制作環境からは記事・資料の本文を開けない。**
- WebFetch は名前解決できずに失敗し、curl はプロキシで 403 になる。
- 出典はすべて「検索抜粋」（検索ツールが返した要約・引用）で確認した。
- PHP 公式（php.net）・The PHP Foundation・JPCERT/CC・国家サイバー統括室の**本文は確認できていない**。
- 公開前に、人が本文を確認することを強く推奨する。

**扱いの決まり：**
- 次の 4 つを区別した：
  1. 脆弱性がある
  2. 悪用されるおそれがある
  3. 攻撃を試みる動きの報告がある
  4. 実際に被害があった
- 停止＝被害、修正版の公開＝対策の完了、とは言わない。

## 4. 事実確認リスト

### FACT-01
- **主張**：PHP は、Web サイトのサーバー側の処理（注文・予約・ログインなど）を作るのに使われるプログラミング言語。PHP で書いたプログラムは、サーバー上の PHP の仕組み（実行環境、インタープリター）が読んで動かす。
- **台本中の該当箇所**：L10「注文は、サーバーというコンピューターに届く」、L11、L12「この裏方の仕事を書く言語の一つが、PHP」、L14「レシピを書く言葉で、それを動かす、厨房の機械でもある」
- **出典**：一般的な技術知識。S3（W3Techs：サーバー側のプログラミング言語として集計）
- **検証結果**：QUALIFIED（簡略化）
- **注意点**：
  - 「レシピ＝言葉、機械＝実行環境」はたとえ。画面に「※たとえ」を出し、直後に本物の流れ（スマホ → サーバー → 結果）を図で見せる。
  - 予約の処理の中身（空きを調べる・記録する・結果を返す）は、一般的な Web アプリの例で、特定のサービスの仕組みではない。
- **修正が必要か**：不要

- **台本中の該当箇所**：L15「サーバー側の言語が分かるサイトの、約七割で使われてる」
- **出典**：S3
- **検証結果**：VERIFIED（検索抜粋）
- **注意点**：
  - **対象は「サーバー側の言語を判別できたサイト」で、すべてのサイトではない**。1 つのサイトが複数の言語を使うこともある。台本はこの範囲どおりに言い、画面に「※W3Techs（2026年8月）。サーバー側の言語が分かるサイトのうち」と出す。
  - 割合は 2025 年 6 月の 74.2% から少しずつ下がっている（検索抜粋）。
- **修正が必要か**：不要

### FACT-03
- **主張**：2026 年 10 月 21 日、PHP の開発チームが、重大な脆弱性 2 件（CVE-2026-109618、CVE-2026-109619。CVSS v4.0 で 9.2、Critical）を修正した版（8.5.12、8.4.27、8.3.36、8.2.35）を公開した。脆弱性の公表と修正版の公開は同じ日。
- **台本中の該当箇所**：L02「きっかけは、PHP」、L17「十月二十一日、重大な弱点が、二つ見つかった」、L28「修正版は同じ日に出た」、L34「更新して、確かめて」
- **出典**：S1, S2, S4, S5
- **検証結果**：QUALIFIED
- **注意点**：
  - 件数・日付・版・CVSS は複数の情報源で一致した（検索抜粋）。
  - 「見つかった」は正確には「公表された」。発見そのものの日付ではない。発見はもっと前で、事前の告知や情報の漏えいがあったと報じられている。台本の「十月二十一日、重大な弱点が二つ見つかった」は、視聴者向けの言い方。画面の札は「2026年10月21日 公表」「重大な脆弱性 2件」とする。
  - PHP の ChangeLog では 22 日付になっているとの指摘もある（当初の公開予定日）。
  - 23 日には、条件の限られた関連の脆弱性（CVE-2026-115560）も公表された。本筋に不要なので台本では扱わない。
- **修正が必要か**：不要（画面の札を「公表」にする）

### FACT-04
- **主張**：今回の脆弱性は、条件がそろうと、認証なし（ログインなし）の外部の攻撃者が、サーバー上で任意のコードを実行できる（リモートコード実行）おそれがある。
- **台本中の該当箇所**：L19「脆弱性は、守りの穴」、L20「条件がそろうと、外からログインなしで、勝手にプログラムを動かされる、おそれがある」
- **出典**：S1, S4, S6, S7
- **検証結果**：VERIFIED（検索抜粋）
- **注意点**：
  - 攻撃には対象側の特定の条件が必要とする解説がある（設定・使い方による）。そのため「条件がそろうと」「おそれがある」と言う。
  - 「必ず乗っ取られる」とは言わない。
  - 裏口の怪しい影は「※イメージ」（実際の攻撃の様子ではない）。
- **修正が必要か**：不要

### FACT-09

- **台本中の該当箇所**：L01「予約も、銀行も、同じ夜に止まった！？」（冒頭の問い）、L29「銀行も予約もゲームも、同じ夜に」

### FACT-10
- **主張**：今回の脆弱性は PHP 本体（コアのインタープリター＝実行環境）にあり、各サイトが書いたプログラム（アプリのコード）の誤りではない。そのため、PHP を使う各社は、自分のサーバーの PHP の版を確かめ、更新する必要があった。PHP という言語そのものが危険になったわけではなく、問題は穴の残った版を使い続けること。
- **台本中の該当箇所**：L22「穴は、店ごとのレシピじゃなく、機械の側」、L24「なってない。守りに穴があっただけ」、L30「店はバラバラでも、機械は同じ型……同じ宿題が出る」、L32「言葉そのものは、危険じゃない。問題は、穴の残った版を、使い続けること」
- **出典**：S1, S4, S6
- **検証結果**：QUALIFIED（簡略化）
- **注意点**：
  - 「PHP core flaws」「core interpreter」と報じられている（検索抜粋）。
  - 一方で、攻撃が成り立つかはサーバーの構成やアプリの使い方にも左右されるとの解説がある。そのため「どの店も必ず危険」とは言わず、「同じ宿題（版を調べて更新する）が出る」とした。
  - 「同じ型」はたとえ。各社の PHP の版や設定は同じとは限らない。
- **修正が必要か**：不要
